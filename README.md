# Customer Churn Data Pipeline — API-Driven Cloud Native Solutions (Assignment 1)

## 1. Business Understanding (Activity 1.1)

**Business problem:** A telecom company wants to identify which customers are
likely to churn (cancel their subscription) so it can proactively target
them with retention offers before they leave. Reducing churn even by a few
percentage points has a large revenue impact because acquiring a new
customer costs far more than retaining an existing one.

**Dataset:** [Telco Customer Churn dataset](https://raw.githubusercontent.com/IBM/telco-customer-churn-on-icp4d/master/data/Telco-Customer-Churn.csv)
(public, IBM sample dataset, mirrored on GitHub) — 7,043 customer records,
21 columns, mix of numeric (tenure, MonthlyCharges, TotalCharges) and
categorical (Contract, PaymentMethod, InternetService, etc.) features, with
`Churn` (Yes/No) as the target.

## 4. Running Each Piece

### 4a. Scheduler (DataOps automation, every 2 minutes)

```bash
cd src
python scheduler.py
```

Leave this running in a terminal (or `tmux`/`screen` session, or as a
background worker in deployment — see Section 6). It logs to
`logs/pipeline.log` and `logs/pipeline_runs.db` on every run.

> **Why not GitHub Actions cron?** GitHub Actions' scheduled workflows have
> a documented minimum interval of 5 minutes and often fire late, so they
> cannot reliably satisfy a strict "every 2 minutes" requirement. Use an
> always-on background worker instead (Section 6).

### 4b. API (Sub-Objective 2)

```bash
cd api
uvicorn main:app --reload --port 8000
```

Open **http://localhost:8000/docs** — this is FastAPI's built-in Swagger UI,
which auto-documents every endpoint's request/response schema. Use it (or
Postman/Insomnia) to test each endpoint below and screenshot the request,
response body, and HTTP status code for Activity 3.3.

| Endpoint | What it shows | Satisfies |
|---|---|---|
| `GET /health` | App version, Python version, uptime, deployment liveness | Deployment info |
| `GET /pipeline/status` | Latest pipeline run stage/status/timestamp | Flow info |
| `GET /pipeline/runs` | Full run history | Flow info |
| `GET /dataset/info` | Dataset shape, columns, source file | Application info |
| `GET /eda/top-features` | Top churn-driving features from latest EDA | Application info |

This gives you 5 distinct application details (assignment requires ≥4).

### 4c. Dashboard (Cloud dashboard)

```bash
cd dashboard
streamlit run app.py
```

Shows the color-coded run history table and the 5 EDA charts, refreshing
as the scheduler produces new runs.

## 5. API Testing Checklist (Activity 3.3)

Using Postman (or `curl` / Swagger UI), for **each** endpoint capture a
screenshot showing:
1. The request (method + URL, and query param for `/pipeline/runs?limit=5`)
2. The JSON response body
3. The HTTP status code (200 for success)
4. One deliberately-broken request showing a non-200 code, e.g.
   `GET /pipeline/status` before any pipeline run exists returns **404**,
   or `GET /nonexistent-route` returns **404**.

Example curl commands to run and screenshot:
```bash
curl -i http://localhost:8000/health
curl -i http://localhost:8000/pipeline/status
curl -i http://localhost:8000/pipeline/runs?limit=5
curl -i http://localhost:8000/dataset/info
curl -i http://localhost:8000/eda/top-features
curl -i http://localhost:8000/nonexistent   # -> 404, for negative-case screenshot
```

## 6. Free-Tier Cloud Deployment (Render)

Render's free tier supports both a **Web Service** (for the API and
dashboard) and a **Background Worker** (for the always-on scheduler) —
push this repo to GitHub, then in Render:

| Service | Type | Start command |
|---|---|---|
| API | Web Service | `uvicorn api.main:app --host 0.0.0.0 --port $PORT` |
| Dashboard | Web Service | `streamlit run dashboard/app.py --server.port $PORT --server.address 0.0.0.0` |
| Scheduler | Background Worker | `python src/scheduler.py` |

All three read/write the same `logs/pipeline_runs.db` — on Render's free
tier each service has its own ephemeral disk, so for the demo either (a)
run the scheduler and API/dashboard together on the **same** service using
a small process manager, or (b) simplest for a graded demo: run all three
in three terminals on your own laptop during the video recording, and
separately deploy the API alone to Render to prove real cloud deployment +
show its public `/docs` URL for the report screenshots.
